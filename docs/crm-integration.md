# Интеграция с CRM: статус уникализации тикета

Для разработчика Свайпера / CRM. Нарезчик (AVE) в автоматическом режиме опрашивает
`montage/<стример>/<эфир>/`, делает 3 версии каждого клипа для TikTok и кладёт их в бакет. CRM узнаёт о
результате, **читая бакет**: новый API не нужен, а бакет — единственный источник истины.

## Где что лежит

Раскладка по контракту `contracts/s3-layout.json` (папки эфиров, с 2026-11-24):

```
montage/<стример>/<эфир>/<имя>.mp4                          ← исходник, его кладёт Свайпер (AVE только читает)
montage/<стример>/<эфир>/<имя>/uniqalized/status.json       ← состояние для CRM
montage/<стример>/<эфир>/<имя>/uniqalized/v1.mp4 … v3.mp4   ← версии
montage/<стример>/<эфир>/<имя>/uniqalized/manifest.json     ← пишется последним: набор готов
```

`<эфир>` — `<id эфира Twitch>_<начало записи>`, например `324159870123_2026-11-20_18-02`.

Клипы, перенесённые до появления папок эфиров (`montage/<стример>/<имя>.mp4`, без папки эфира),
обрабатываются по-старому, их версии лежат в `montage/<стример>/uniqalized/<имя>/`. Где именно лежат
версии конкретного клипа, всегда видно по `folder` в webhook и по путям в `status.json`.

`<имя>` — имя файла исходника без расширения. Если в одной папке лежат два исходника с одним
именем и разными расширениями (`clip.mp4` и `clip.mov`), папка называется с расширением (`clip.mov`).
Подпапку `.partial/` внутри папки клипа CRM должна игнорировать: там временные файлы.

## Что AVE читает из метаданных исходника (Свайпер)

AVE читает метаданные HEAD-запросом в начале обработки клипа:

| Метаданные | Что делает AVE |
|---|---|
| `clip-id` | возвращает в `status.json` (`clipId`, `clip_id`), `manifest.json` и метаданные каждой версии |
| `webcam-region` `x,y,w,h` | вебка для split screen; автоопределение вебки не используется |
| `stream-region` `x,y,w,h` | игровая картинка: нижняя часть split screen вырезается из этой области |
| `montage-mode` `cut` | паузы вырезаются; клип длиннее 3 минут обрезается до лучшего фрагмента до 90 с |
| `montage-mode` `full` | клип целиком, паузы не вырезаются (хук в начале v2 остаётся) |
| `stream-id` | записывается в `manifest.json` |
| `swiper-source` | игнорируется |

Нет областей (человек нажал «Пропустить», клип старой раскладки) — AVE определяет вебку сам.
Неверное значение (не четыре числа от 0 до 1, область за краем кадра, неизвестный режим) игнорируется
с записью в лог, как будто его нет. В `manifest.json` видно, что использовалось:
`"regions": {"webcam": "…", "stream": "…", "source": "swiper" | "auto"}`, `"montage_mode": "cut" | "full"`.

## Поля для Свайпера

`status.json` содержит поля Свайпера и поля CRM одновременно:

```json
{"status": "processing", "clipId": "8d7f3a2c9c1e6f4a", "attempts": 1,
 "state": "processing", "clip_id": "8d7f3a2c9c1e6f4a", "source": {"key": "…", "etag": "…"}, "updated": "…"}
```

- `status`: `processing`, `failed` или `done`. Ожидание сервера распознавания или сети — тоже
  `processing` (с `reason`), а в `state` — `waiting`.
- `attempts` — номер попытки для текущего файла (ETag): 1, 2, 3. После трёх неудач клип отложен
  (`parked: true`) до замены файла.
- При ошибке: `"status": "failed"`, `"reason": "…"` (то же в `error`).
- `status.json` пишется до скачивания. Если исходник пропал (Свайпер унёс клип обратно в `to_sort/`)
  во время скачивания или рендера, AVE бросает задачу, ничего не выкладывает и удаляет `status.json`.

`manifest.json` содержит `version: 1`, `clipId`, `source.key`, `source.etag` и `variants[].key` по контракту
Свайпера, плюс поля CRM (`manifest_version`, `clip_id`, размеры, MD5, длительности, описание версий).

## Как найти тикет

1. **По `clip-id` (основной способ).** Автоклиппер пишет `clip-id` в метаданные каждого файла
   (`x-amz-meta-clip-id`), при переносе в `montage/` он сохраняется. AVE копирует его в
   `status.json`, `manifest.json` и метаданные каждой версии. Нужно, чтобы Свайпер при создании тикета из
   `to_sort/` сохранял `clip-id` (запрос HEAD объекта, поле `Metadata["clip-id"]`).
2. **По пути исходника (запасной способ).** `source.key` в `status.json`/`manifest.json` — полный путь
   исходника в `montage/`. Папка версий лежит рядом с исходником и называется так же, как его файл:
   `<имя>.mp4` → `<имя>/uniqalized/`.

## Состояния

| Что в бакете | `status.json` → `state` | Статус тикета |
|---|---|---|
| исходник в `montage/<стример>/<эфир>/`, папки клипа ещё нет | — | Ждёт уникализации |
| AVE взял клип в работу | `processing` | Уникализируется |
| сервер распознавания речи или сеть недоступны, клип ждёт | `waiting` (+ `reason`) | Уникализируется (задержка) |
| `manifest.json` есть и `manifest.source.etag` == ETag исходника | `done` | Готово: 3 ссылки из `manifest.variants[].key` |
| клип не обработался | `failed` (+ `error`, `failures`, `parked`) | Ошибка уникализации |

`parked: true` — AVE отложил клип после 3 неудач подряд и не возьмётся за него, пока файл исходника не
заменят.

## Правила

- **Готовность — только по `manifest.json`**, причём только если `manifest.source.etag` совпадает с
  текущим ETag исходника. Наличие mp4-файлов ничего не значит: при повторной обработке AVE сначала
  удаляет манифест и старые версии, потом выкладывает новые и последним пишет манифест.
- `status.json` — подсказка для отображения, а не доказательство готовности. Если `state: done`, но
  манифеста нет или ETag другой, значит, идёт пересборка: считать «Уникализируется».
- Исходник из `montage/` нельзя переносить или удалять, пока его версии нужны: связь держится на пути
  и `clip-id`.

## Webhook: мгновенное уведомление о публикации

Опрашивать бакет не обязательно: если в `.env` AVE задан `AVE_WEBHOOK_URL`, после записи `manifest.json`
и `status.json` (`done`) AVE отправляет на этот адрес `POST`. Бакет остаётся источником истины: если
webhook не дошёл, публикация не отменяется.

Заголовки:

| Заголовок | Значение |
|---|---|
| `Content-Type` | `application/json` |
| `X-AVE-Event` | `published` |
| `X-AVE-Event-Id` | `<clip_id>:<etag исходника>` (без clip-id: `<ключ исходника>:<etag>`) |
| `X-AVE-Signature` | `sha256=<HMAC-SHA256 тела запроса ключом AVE_WEBHOOK_SECRET, hex>`; только если секрет задан |

Тело:

```json
{"event": "published", "event_id": "a7cdbf5a-…:d8773630…-8", "clip_id": "a7cdbf5a-…",
 "source": {"key": "montage/buster/324159870123_2026-11-20_18-02/…mp4", "etag": "d8773630…-8", "size": 63611757, "last_modified": "…"},
 "folder": "montage/buster/324159870123_2026-11-20_18-02/2026-11-20_21-59-44_reaction_6f4a/uniqalized",
 "versions": ["…/v1.mp4", "…/v2.mp4", "…/v3.mp4"],
 "manifest_key": "…/manifest.json", "status_key": "…/status.json",
 "manifest": {"manifest_version": 1, "…": "полный manifest.json"}}
```

Что делать CRM:

1. Проверить подпись: посчитать HMAC-SHA256 от **сырых байтов тела** тем же секретом и сравнить
   с `X-AVE-Signature` за постоянное время (`hmac.compare_digest`).
2. Найти тикет по `clip_id`, если его нет, то по `source.key`, и перевести в «версии готовы».
3. Ответить `2xx` быстро (до 15 секунд). Тяжёлую работу делать после ответа.
4. Повторы нормальны: одно событие может прийти больше одного раза. Если `event_id` уже обработан,
   ответить `200` и ничего не менять. Если исходник заменили и перерендерили, придёт новое событие
   с новым etag в `event_id`.

Ответы и повторы:

- `2xx`: доставлено.
- Ошибка сети, `5xx`, `408`, `429`: AVE повторит через 30 с, 1, 2, 4 … минуты, не реже раза в час,
  в том числе после перезапуска (очередь лежит в `webhook.json` рядом с `state.json`).
- Другие `4xx`: AVE считает, что CRM отклонила само событие, и больше его не шлёт (пишет в лог и
  в `webhook.json`, раздел `rejected`). Статус тикета тогда берите из `status.json`.

Настройка на стороне AVE (`.env`):

```
AVE_WEBHOOK_URL=https://crm.example/api/ave/events
AVE_WEBHOOK_SECRET=<общий секрет, тот же в CRM>
```

Пример проверки на Python:

```python
import hashlib, hmac

def valid(raw_body: bytes, header: str, secret: str) -> bool:
    expected = "sha256=" + hmac.new(secret.encode(), raw_body, hashlib.sha256).hexdigest()
    return hmac.compare_digest(expected, header or "")
```
